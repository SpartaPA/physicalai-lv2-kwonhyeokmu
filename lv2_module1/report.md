### 1-2. 펌웨어 빌드와 업로드

빌드와 업로드를 모두 라즈베리파이에서 수행했다. OpenCR 공식 업로더는
x86_64 바이너리만 배포되므로, **업로더 `opencr_ld`도 Pi에서 ARM용으로
직접 빌드**했다.

| 항목 | 값 |
|---|---|
| 소스 | `examples/opencr_position_p/opencr_position_p.ino` |
| 툴체인 | `arm-none-eabi-gcc` 10.3.1 (15:10.3-2021.07-4) |
| 산출물 | `opencr_position_p.ino.bin`, 104,844 바이트 (2026-09-22 20:28) |
| SHA-256 | `6a3629a8070a5d1f55dce837cc90f073db4444b83da5c722133446608a8151e3` |
| 업로더 | `opencr_ld`, 38,856 바이트, ELF 64-bit ARM (Pi에서 빌드) |

업로드 결과(`results/upload.log` 전문):

```
Board Name : OpenCR R1.0
Board Ver  : 0x17020800
flash_erase : 0 : 0.955000 sec
flash_write : 0 : 1.162000 sec
CRC OK 9B55F6 9B55F6 0.003000 sec
[OK] Download
jump_to_fw
jump finished
```

**성공 판정의 근거는 `CRC OK`다.** 앞의 `9B55F6`은 전송한 이미지에서 계산한
값이고, 뒤의 `9B55F6`은 보드 플래시에 실제로 기록된 내용을 다시 읽어 계산한
값이다. 두 값이 일치하므로 보드에 들어간 내용이 손상 없이 일치함이 증명된다.
파일 자체의 SHA-256은 "내 디스크의 파일이 온전한가"만 말해 줄 뿐 업로드
성공의 증거가 아니므로, 둘을 구분해 기재했다.

업로드 직후 `/dev/ttyACM0`의 생성 시각이 20:38:54로 갱신되었다. `jump_to_fw`로
보드가 재부팅되면서 USB가 다시 열거되었다는 뜻이며, 새 펌웨어가 실제로
실행되었음을 뒷받침한다.

### 1-3. 실행 A 설정

`results/실행A.log`의 머리 부분이 설정 증거다.

```
# 2026-09-23 11:14:52 KST  >>> s 2.0 10 10
START: current position = 0 deg.
P SET Kp=2.0000, Ki=0.0000, Kd=0.0000, speed_limit_deg_s=10.000, angle_deg=10.000
Run timeout [s]: 60.0
```

| 설정 | 값 | 단위 | 비고 |
|---|---|---|---|
| 비례 게인 Kp | 2.0 | 1/s | 오차[°]를 속도 명령[°/s]으로 바꾸는 환율 |
| 적분 Ki / 미분 Kd | 0 / 0 | — | 이 펌웨어는 **P 제어 전용**, 변경 불가 |
| 속도 상한 | 10 | °/s | |
| 목표각 | +10 | ° | **상대각**. `START` 시점의 위치가 0°가 된다 |
| 실행 시간 | 60 | s | 종료 시 자동 정지 |

목표각이 절대 각도가 아니라 **시작 위치 기준 상대각**인 점이 중요하다.
펌웨어는 `START` 순간의 엔코더 값을 원점으로 기억하고, 이후 2초 동안은
목표를 0°로 유지하다가 `t = 2.0 s`에 +10°로 바꾼다. 따라서 목표 변경 시점이
로그 안에 명확히 남는다.

### 1-4. 목표값·측정값·제어 출력의 구분과 단위

로그 한 행의 컬럼을 성격별로 분류하면 다음과 같다.

| 분류 | 컬럼 | 단위 | 의미 |
|---|---|---|---|
| **목표값** | `target_deg` | ° | 제어기가 도달하려는 상대 각도 |
| **측정값** | `position_deg` | ° | 엔코더가 읽은 현재 각도 (분해능 0.088°) |
| **측정값** | `speed_deg_s` | °/s | 엔코더가 읽은 현재 각속도 |
| 오차 | `error_deg` | ° | 목표값 − 측정값 |
| **제어 출력(계산)** | `p_deg_s`, `pid_deg_s` | °/s | Kp × 오차. 제어기가 "내고 싶은" 속도 |
| **제어 출력(실제)** | `u_deg_s` | °/s | 상한과 정수 변환을 거쳐 모터에 **실제로 나간** 속도 명령 |
| 설정 | `v_limit_deg_s`, `kp`, `ki`, `kd` | °/s, 1/s | |
| 시간 | `dt_ms`, `t_s` | ms, s | 제어 주기 실측값, 경과 시간 |

**`pid_deg_s`와 `u_deg_s`를 반드시 구분해야 한다.** 전자는 제어 계산의 결과이고
후자는 속도 상한과 하드웨어 분해능을 통과한 뒤 실제로 전송된 값이다. 아래에서
보듯 두 값이 크게 달라지는 구간이 존재한다.

### 1-6. 실제 움직임 설명

목표 +10°에 대해 모터는 1.8초 만에 9.756°까지 이동한 뒤 0.244°의 오차를
남기고 멈췄다. 속도 명령의 분해능이 1.374 °/s여서 오차가 0.344° 아래로
내려가면 명령이 0으로 반올림되기 때문이며, P 제어에는 이를 지울 적분항이
없다.

---

아래는 위 두 문장의 근거다. 움직임은 세 국면으로 나뉜다.

| 국면 | 구간 | 현상 | 로그 근거 |
|---|---|---|---|
| ① 속도 포화 | t = 2.0 ~ 2.5 s | 오차가 커서 제어 출력 19.824 °/s가 상한에 잘림. 일정한 속도로 부드럽게 회전한다 | `u_deg_s`가 9.618로 고정 |
| ② 감속 | t = 2.5 ~ 3.8 s | 오차가 5° 아래로 내려가 포화가 풀리고 속도가 계단식으로 줄어든다 | `u_deg_s` 9.618 → 1.374 |
| ③ 잔류 오차 | t = 3.8 s 이후 | 0.244°를 남긴 채 정지한다 | `pid_deg_s`는 0.488인데 `u_deg_s`는 0 |

③에서 **제어기는 계속 "더 가라"고 계산하는데 명령이 모터에 닿지 않는다.**
원인은 속도 명령의 정수 분해능이다. 스케치의 상수

```c
constexpr float RAD_S_PER_VELOCITY_RAW = 0.229f * 2.0f * PI_F / 60.0f;
```

에서 1칸은 0.229 rpm = **1.374 °/s**이고, 실제로 로그의 `u_deg_s`도 0, 1.374,
2.748, 4.122 … 1.374의 배수만 나타난다. 정수 변환에서 반올림이 일어나므로
0.5칸(= 0.687 °/s) 미만의 명령은 0이 된다. 따라서 정지 조건은

> Kp × 오차 < 0.687 °/s  ⟹  **오차 < 0.687 / Kp**

Kp = 2.0이면 0.344° 미만에서 멈추며, 실측 잔류 오차 0.244 ~ 0.332°가 이 범위
안에 들어온다. ①에서 실제 명령이 10.000이 아니라 9.618인 것도 같은 이유다
(`10 ÷ 1.374 = 7.28` → 7칸 → `7 × 1.374 = 9.618 °/s`). **이 조건을 Kp = 0.5로
바꿔 검증한 내용은 문제 3에 있다.**

측정 분해능은 원인이 아니다. 엔코더는 1회전 4096틱이라 0.088°까지 읽을 수 있어
잔류 오차보다 훨씬 세밀하다. **위치는 정밀하게 읽히지만 미는 힘을 그만큼 잘게
나눌 수는 없다**는 것이 이 현상의 본질이며, 근본적으로는 적분항이 없는 P 제어의
정상상태 오차다.

**관찰 하나 더 — 정지 후의 1틱 떨림**

정지 구간에서도 제어 루프는 100 Hz로 계속 돈다. 두 실행 모두 `t = 10 s` 이후
500행 내내 `u_deg_s`는 0이었는데, `position_deg`는 한 값에 고정되지 않고 **두 값
사이만 오갔다**(Kp 2.0에서 9.668 / 9.756, Kp 0.5에서 8.701 / 8.789). 간격이
엔코더 1틱과 정확히 같고 그 사이 모터로 나간 명령은 0이므로, 축이 실제로 움직인
것이 아니라 **엔코더 최하위 비트의 읽기 잡음**이다. 잔류 오차를 하나의 값이 아니라
범위로 적은 것도 이 때문이다.

그래도 정지는 "제어를 끈 상태"가 아니다. **명령이 분해능 아래로 내려가 0으로
반올림된 상태**일 뿐이어서, 축을 손으로 미는 것 같은 외란으로 오차가
`0.687 / Kp`를 넘어서면 곧바로 1칸이 다시 나간다.

## 문제 2. 오차와 피드백 해석

### 2-1. 시점별 목표각·현재각·오차

`results/실행A.log`에서 세 시점을 골랐다. 오차는 `오차 = 목표각 − 현재각`으로
계산했고, 단위는 모두 도(°)다.

| 시점 | t [s] | 목표각 [°] | 현재각 [°] | 오차 [°] | 상태 |
|---|---|---|---|---|---|
| 초기 | 2.000 | 10.000 | 0.088 | **+9.912** | 목표 변경 직후, 속도 포화 |
| 중간 | 2.500 | 10.000 | 4.219 | **+5.781** | 상한 속도로 이동 중 |
| 마지막 | 59.907 | 10.000 | 9.756 | **+0.244** | 정지, 잔류 오차 |

검산: `10.000 − 0.088 = 9.912`, `10.000 − 4.219 = 5.781`,
`10.000 − 9.756 = 0.244`.

"중간" 시점으로 실행 시간의 중앙인 t = 30 s를 쓰지 않은 이유는, 그 시점이 이미
정지 이후여서 오차가 마지막과 동일해 변화를 보여 주지 못하기 때문이다. 오차가
실제로 변하는 과도 구간에서 골랐다.

### 2-2. 오차 크기의 변화

오차는 +9.912 → +5.781 → +0.244로 **단조 감소**하며, 부호는 계속 양수다.
현재각이 목표각을 한 번도 넘지 않았다는 뜻이고, 오버슈트 없이 접근했음을
의미한다.

감소 속도는 일정하지 않다. 초기 0.5초 동안 4.131° 줄어(약 8.3 °/s) 속도 상한에
가깝게 움직였고, 이후 오차가 작아질수록 제어 출력도 함께 작아져 감속했다.
**오차가 줄면 미는 힘도 줄어드는 것이 비례 제어의 정의**이며, 그 결과 목표
부근에서 스스로 속도를 낮춰 부드럽게 멈춘다.

다만 오차는 0으로 수렴하지 않고 0.244°에서 멈춘다. 이유는 1-6에서 설명한
속도 명령 분해능(1칸 = 1.374 °/s)이다.

### 2-3. 위치 측정값을 얻는 센서와 OpenCR까지의 통신 경로

**센서:** 위치는 별도의 외부 센서가 아니라 **DYNAMIXEL XM430-W350에 내장된
자기식 엔코더**에서 얻는다. 1회전을 4096틱으로 분해하므로 1틱 = 360/4096 =
**0.088°**이며, 로그의 `position_deg`가 모두 이 값의 배수로 나타나는 것이 그
증거다. 모터 내부 MCU가 이 값을 컨트롤 테이블의 `Present Position`
항목에 갱신한다.

**통신 경로(측정값이 올라오는 방향):**

```
XM430-W350 내장 자기 엔코더
        │  (모터 내부 MCU가 컨트롤 테이블에 기록)
        ▼
DYNAMIXEL 컨트롤 테이블  Present Position / Present Velocity
        │  Protocol 2.0 READ 패킷 응답
        │  TTL 반이중 3선 버스, 1 Mbps, ID 12
        ▼
OpenCR 1.0  DXL 포트 (Serial3 + 방향 제어 핀 84)
        │  dxl.readControlTableItem(...)
        ▼
OpenCR MCU (STM32F746)  ── 여기서 오차와 제어 출력을 계산 (100 Hz)
        │  Serial.print(...)  115200 bps
        ▼
USB CDC 가상 COM 포트 (0483:5740)
        ▼
라즈베리파이  /dev/ttyACM0
        │  lv2_module1/run.py (pyserial)
        ▼
results/실행A.log
```

**명령이 내려가는 방향**은 이 경로의 역순이다. 라즈베리파이가
`s 2.0 10 10` 문자열을 `/dev/ttyACM0`으로 보내면 OpenCR이 이를 해석해 설정을
바꾸고, 매 제어 주기마다 계산한 속도 명령을 `setGoalVelocity`로 같은 TTL
버스를 통해 모터에 전달한다.

TTL 버스가 **반이중(half-duplex)**이라는 점이 중요하다. 한 가닥의 데이터 선을
송신과 수신이 번갈아 쓰므로, OpenCR은 방향 제어 핀(84번)으로 매 패킷마다
송수신 방향을 전환한다. 스케치의 `Dynamixel2Arduino dxl(Serial3, 84)`에서
두 번째 인자가 그 핀이다.

또한 **제어 루프는 라즈베리파이가 아니라 OpenCR 안에서 닫힌다.** 라즈베리파이는
설정을 보내고 로그를 받아 적을 뿐이며, 오차 계산과 속도 명령 생성은 모두
OpenCR MCU가 100 Hz로 수행한다(로그의 `dt_ms`가 약 10.000 ms로 일정하다).
따라서 SSH 연결이 끊겨도 제어 자체는 계속되며, 정지는 `x` 명령이나 60초
타임아웃, 또는 모터의 버스 워치독으로 이루어진다.

### 2-4. 목표 +30°, 현재각 +35°인 경우

**오차의 부호:**

> 오차 = 목표각 − 현재각 = 30° − 35° = **−5°  (음수)**

현재각이 목표를 5° 지나친 상태이므로 오차가 음수가 된다.

**양의 Kp에 의한 보정 방향:**

Kp = 2.0을 적용하면 제어 출력은

> 2.0 × (−5°) = **−10 °/s**

속도 명령이 음수이므로 모터는 **지금까지 돌던 방향과 반대로 회전**한다. 즉
35°에서 30° 쪽으로 되돌아오며, 각도가 줄어들수록 오차의 크기도 줄어 명령이
약해지고, 30° 부근에서 멈춘다.

핵심은 **부호가 방향을 결정한다**는 점이다. Kp가 양수인 한, 목표에 못 미치면
오차가 양수가 되어 전진 명령이, 목표를 지나치면 오차가 음수가 되어 후진
명령이 자동으로 생성된다. 목표에서 벗어난 쪽과 반대로 밀어 주는 이 성질이
피드백 제어를 안정하게 만든다. 만약 Kp가 음수라면 벗어난 방향으로 더 밀어
발산할 것이다.

## 문제 3. P 게인 변경에 따른 응답 비교

### 3-1. 실행 A·B 설정

발제가 요구한 "목표각·속도 상한·부하·측정 주기 유지"를 맞추기 위해 **Kp만
바꾸고 나머지 조건은 모두 고정**했다. 두 실행 모두 장비를 움직이지 않은 상태에서
연달아 수행했다.

| 항목 | 실행 A | 실행 B | 비고 |
|---|---|---|---|
| 기록 | `results/실행A.log` | `results/실행B.log` | 각 604행 |
| **Kp** | **2.0** | **0.5** | 유일하게 바꾼 값 |
| Ki / Kd | 0 / 0 | 0 / 0 | 펌웨어에서 고정 |
| 목표각 | +10° (상대) | +10° (상대) | 동일 |
| 속도 상한 | 10 °/s | 10 °/s | 동일 |
| 측정·제어 주기 | 100 Hz (`dt_ms` 약 10.0) | 100 Hz | 동일 |
| 부하·시작 자세 | 무부하, 직전 정지 위치 | 무부하, 직전 정지 위치 | 동일 |
| 실행 시간 | 60 s | 60 s | 동일 |

시작 자세는 펌웨어가 `START` 시점의 엔코더 값을 원점으로 잡으므로 두 실행 모두
0°에서 출발하며, 이동 여유도 +10°로 같다.

### 3-2. 같은 경과 시간에서의 현재각과 목표 초과 여부

경과 시간은 목표가 +10°로 바뀐 `t = 2.0 s`를 0으로 놓고 센 값이다.

| 경과 | A 현재각 | A 오차 | B 현재각 | B 오차 | 목표 초과 |
|---|---|---|---|---|---|
| 0.0 s | 0.088° | 9.912° | 0.000° | 10.000° | 없음 |
| 0.2 s | 1.143° | 8.857° | 0.791° | 9.209° | 없음 |
| 0.5 s | 4.219° | 5.781° | 2.021° | 7.979° | 없음 |
| 1.0 s | 7.998° | 2.002° | 3.779° | 6.221° | 없음 |
| 1.5 s | 9.229° | 0.771° | 5.098° | 4.902° | 없음 |
| 2.0 s | 9.756° | 0.244° | 6.240° | 3.760° | 없음 |
| 3.0 s | 9.756° | 0.244° | 7.559° | 2.441° | 없음 |
| 3.7 s | 9.756° | 0.244° | 8.613° | 1.387° | 없음 |
| 10.0 s | 9.668° | 0.332° | 8.701° | 1.299° | 없음 |
| 57.9 s | 9.756° | 0.244° | 8.701° | 1.299° | 없음 |

**목표 초과는 두 실행 모두 한 번도 없었다.** 최대 위치는 A가 9.756°, B가
8.789°로, 둘 다 목표 +10°에 미치지 못한 채 접근만 했다.

요약하면 다음과 같다.

| 지표 | A (Kp 2.0) | B (Kp 0.5) |
|---|---|---|
| 목표의 90%(9.0°) 도달 | 1.40 s | **끝내 도달하지 못함** |
| 속도 명령이 0이 된 시각 | 1.80 s | 3.70 s |
| 잔류 오차 | 0.244 ~ 0.332° | 1.211 ~ 1.299° |
| 최대 속도 명령 | 9.618 °/s (상한에서 포화) | 5.496 °/s (포화 없음) |
| 목표 초과 | 없음 | 없음 |

### 3-3. 차이의 근거

**① 초기 속도가 다른 이유 — 속도 상한에 닿는지 여부**

목표 변경 직후 오차는 두 실행 모두 약 10°다. 제어 출력은 `Kp × 오차`이므로

- A: `2.0 × 9.912 = 19.824 °/s` → 상한 10 °/s에 걸려 **9.618 °/s로 잘림**
- B: `0.5 × 10.000 = 5.000 °/s` → 상한보다 낮아 **잘리지 않음**

즉 **속도 상한은 A에서만 실제로 작동하는 제약**이다. B는 60초 내내 상한에 닿은
적이 없고, 로그 전체에 나타난 속도 명령은 1.374 / 2.748 / 4.122 / 5.496 네
가지뿐이다.

**② 잔류 오차가 약 5배 차이 나는 이유 — 정지 조건이 Kp에 반비례**

§1-6에서 유도한 정지 조건 `오차 < 0.687 / Kp`를 두 실행에 적용하면

| Kp | 예측 상한 | 실측 잔류 오차 | 일치 |
|---|---|---|---|
| 2.0 | 0.344° | 0.244 ~ 0.332° | 일치 |
| 0.5 | 1.374° | 1.211 ~ 1.299° | 일치 |

Kp를 4배 올리니 잔류 오차의 상한도 정확히 1/4로 줄었다. 여기서 나오는 결론이
이 비교의 핵심이다. **게인이 낮으면 단순히 느린 것이 아니라, 애초에 도달할 수
없는 영역이 넓어진다.** B는 60초를 주었는데도 목표의 90%에 닿지 못하고
8.701°에서 멈췄다. 시간을 더 주어도 결과는 같다.

**③ 두 실행 모두 목표를 초과하지 않은 이유**

P 제어는 오차의 부호가 바뀌어야만 반대 방향 명령을 낸다. 두 실행 모두 오차가
양수인 상태에서 명령이 0으로 떨어져 멈췄으므로 목표를 넘어설 기회가 없었다.
적분항이 있었다면 누적된 값 때문에 목표를 넘겼을 수 있으나, 이 펌웨어는 Ki가 0
으로 고정되어 있다.

### 3-4. 변경한 게인이 어디에 있는 게인인가

**이번에 바꾼 Kp는 OpenCR의 위치 제어 게인이다.** 다이나믹셀 내부 게인이 아니다.

근거는 두 가지다.

1. `s 2.0 10 10` 명령은 OpenCR 스케치의 시리얼 파서가 받아 스케치 변수에 저장한다.
   다이나믹셀 컨트롤 테이블에 쓰는 동작은 펌웨어 어디에도 없다.
2. 로그의 `kp:2.0000` 컬럼은 OpenCR이 자기 변수를 출력한 값이며, 오차 계산과
   `pid_deg_s` 산출도 모두 OpenCR MCU에서 이루어진다.

이 시스템은 **이중 루프** 구조다.

| 루프 | 도는 곳 | 하는 일 | 이번에 바꾼 것 |
|---|---|---|---|
| 바깥 · 위치 루프 | OpenCR (100 Hz) | 오차 → 속도 명령 (P 제어) | **여기** |
| 안쪽 · 속도 루프 | 다이나믹셀 내부 MCU | 속도 명령 → 전류·PWM | 손대지 않음 |

펌웨어가 모터를 `OP_VELOCITY`(속도 모드)로 구동하기 때문에 모터는 **속도** 명령만
받으며, 그 속도를 실제로 맞추는 일은 모터 내부 게인이 담당한다. XM430-W350의
컨트롤 테이블에도 Position/Velocity PID 게인이 따로 있지만 이번 과제에서는 읽지도
쓰지도 않았다.

### 3-5. I항과 D항의 역할

- **I항(적분)** — 시간에 따라 쌓인 오차를 누적해 출력에 더하므로, P만으로는
  영원히 남는 정상상태 오차(이번 실험의 0.244°와 1.299°)를 0까지 밀어 없앤다.
- **D항(미분)** — 오차가 줄어드는 속도에 반응해 목표에 빠르게 접근할 때 미리
  제동을 걸므로, 오버슈트와 정착 직후의 진동을 줄인다.

## 문제 4. 제어와 통신의 역할 해석

> 이 문항의 기록은 **발제가 제공한 설명용 가상 기록**이며 실제 실행 결과가 아니다.
> 목표와 현재값의 단위는 **°(도)**로, 8강에서 다룬 RPM 속도 인터페이스와는 다른
> 인터페이스다.

### 4-1. 구조도와 신호의 방향

```
┌──────────────────────────────────────────────────────────────┐
│  PC — ROS 2 노드                                             │
│    publish  /motor/target  [°]     subscribe  /motor/state   │
└───────┬──────────────────────────────────────▲───────────────┘
        │ 목표 ↓                      측정값 ↑ │   DDS
┌───────▼──────────────────────────────────────┴───────────────┐
│  micro-ROS Agent — 라즈베리파이                              │
│    DDS ↔ 직렬(XRCE-DDS) 변환·중계                            │
└───────┬──────────────────────────────────────▲───────────────┘
        │ 목표 ↓                      측정값 ↑ │   USB 시리얼
┌───────▼──────────────────────────────────────┴───────────────┐
│  OpenCR 1.0 — micro-ROS 클라이언트                           │
│    ★ 제어 계산 10 ms 주기 : 오차와 속도 명령을 여기서 만든다 │
│    ★ 상태 발행 100 ms 주기                                   │
└───────┬──────────────────────────────────────▲───────────────┘
        │ 속도 명령 ↓              현재 위치 ↑ │   TTL 반이중 1 Mbps
┌───────▼──────────────────────────────────────┴───────────────┐
│  다이나믹셀 XM430-W350 (ID 12)                               │
│    내부 속도 루프 + 엔코더 4096틱/회전                       │
└──────────────────────────────────────────────────────────────┘
```

- **목표 전달 방향(아래로):** PC → Agent → OpenCR → 모터
- **측정값 반환 방향(위로):** 모터 엔코더 → OpenCR → Agent → PC

**제어 루프는 OpenCR 안에서 닫힌다.** PC는 목표를 주고 상태를 받아 볼 뿐 오차
계산에는 관여하지 않는다.

### 4-2. 목표와 상태를 보내고 받는 주체

| 토픽 | 보내는 쪽 | 받는 쪽 | 주기 |
|---|---|---|---|
| `/motor/target` | PC의 ROS 2 노드 (publisher) | OpenCR의 micro-ROS 클라이언트 (subscriber) | 필요할 때. 기록상 0.0초에 1회 |
| `/motor/state` | OpenCR (publisher) | PC의 ROS 2 노드 (subscriber) | 100 ms 고정 |

micro-ROS Agent는 **어느 쪽의 주체도 아니다.** PC 쪽 DDS 네트워크와 OpenCR 쪽
직렬 링크 사이에서 메시지를 번역해 중계할 뿐이다. 다만 Agent가 멈추면 양방향
통신이 모두 끊긴다.

### 4-3. 상태 발행 한 주기 동안의 제어 계산 횟수

```
100 ms ÷ 10 ms = 10회
```

**상태가 한 번 발행되는 동안 OpenCR은 제어를 10번 계산한다.** 제공된 기록으로
확인하면 PC는 0.5초에 12.0°, 1.0초에 22.0°를 받았다. 그 0.5초 구간에서 PC가 본
값은 5개뿐이지만 OpenCR은 50번 계산했다.

여기서 결론이 둘 나온다.

1. **PC가 보는 값은 항상 최대 100 ms 오래된 값이다.** 0.1초에 수신한 2.0°는 그
   순간의 실제 위치가 아니라 직전 발행 시점의 위치다. PC 로그만 보고 응답 속도를
   평가하면 실제보다 느리게 보인다.
2. **PC를 제어 루프 안에 넣으면 안 된다.** 100 ms 주기로 오는 값에 맞춰 PC가
   오차를 계산하면 제어 주기가 10 ms에서 100 ms로 10배 느려지고 통신 지연까지
   더해져 진동하기 쉽다. 제어를 OpenCR에 둔 구조가 이 문제를 피한다.

### 4-4. 통신 단절 시 오래된 명령의 처리 정책

**정책 — 마지막 목표를 받은 뒤 일정 시간(예: 300 ms, 상태 발행 주기의 3배)이
지나도 새 목표가 오지 않으면 OpenCR은 오래된 목표를 버리고 속도 명령을 0으로
만든 뒤 정지 상태를 유지한다.** 통신이 복구되면 새 목표를 받은 시점부터 다시
동작하며, 끊긴 동안 밀린 명령은 실행하지 않는다.

이유는 세 가지다.

1. **오래된 목표는 이미 틀린 목표다.** 목표는 보낸 그 시점의 상황에 대한
   판단이므로, 끊긴 동안 상황이 바뀌었을 수 있다. 끊긴 줄 모르고 옛 목표를 계속
   추종하면 로봇은 아무도 원하지 않는 동작을 이어 간다.
2. **정지가 가장 안전한 기본 동작이다.** 이 과제처럼 축이 고정된 장비에서도,
   조작자가 멈출 수단을 잃은 상태에서 모터가 계속 도는 것은 위험하다.
3. **밀린 명령을 몰아서 실행하면 급격한 움직임이 된다.** 복구 직후 큰 오차가
   한꺼번에 들어오면 제어 출력이 상한까지 튀어 예상보다 빠르게 움직인다. §1-6에서
   관찰한 포화 구간이 바로 그런 상황이며, 그것이 통신 복구 순간에 일어나면 사람이
   예측하기 어렵다.

반대로 **상태 발행이 끊기는 것은 제어를 멈출 이유가 되지 않는다.** 제어 루프는
OpenCR 안에서 닫혀 있고 위치는 TTL 버스로 직접 읽으므로, PC가 상태를 받지 못해도
제어 자체는 정상이다. 단절에 대비해야 하는 쪽은 목표가 내려오는 경로다.
